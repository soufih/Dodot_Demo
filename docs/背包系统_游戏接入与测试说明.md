# 背包系统游戏接入与测试说明

验证日期：2026-11-07。验证环境：Windows、Godot 4.7.2。

## 已接入的流程

正式玩家 `Scene/Hero/Hero.tscn` 已挂载 `PlayerInventoryComponent`。现有怪物掉落、角色掉落及调试掉落共用 `DropComponent.create_dropped_item()`，现在会把配置 ID、数量传入世界掉落场景。玩家靠近后沿用已有交互区域和 E 键拾取；Tab 沿用项目的 `OpenBackpack` 动作，经现有 UIManager 打开正式背包工作区。

背包业务状态仍由 InventoryManager 唯一持有，角色和窗口不会各自保存物品副本作为另一套状态。新增控件、拾取区域和测试台节点均在 `.tscn` 中声明；代码只实例化已有场景、绑定数据和处理行为。

```text
DropComponent → DroppedItem（配置 ID、待拾取数量）
                         ↑
E → InputController → InteractionController → PickupInteractable
                                               ↓
                                  PlayerInventoryComponent.receive_item()
                                               ↓
                         InventoryManager.quick_add_to_container()
                                               ↓
                                 GridService / SlotService

Tab → PlayerInventoryComponent → UIManager → inventory_workspace.tscn
                                               ↓
                                绑定容器快照、订阅变更通知
```

`InventoryService` 的抽象接口及子类实现分工保持不变。Manager 负责创建新增物品的 ItemInstance；角色、掉落和交互模块只传配置 ID 与数量。`can_stack`、`can_place` 保持现有 ItemInstance 查询参数。

## 接收与数量规则

角色业务入口：

```gdscript
receive_item(config_id: int, quantity: int) -> InventoryResult
```

成功时 `payload` 是**实际接收的数量**，`affected_ids` 为新增实例 ID；空间不足时可以部分成功。例如 2 × 1 测试背包接收材料 21 ×250，会先放入两栈各 100，返回接收数量 200，地面保留 50。

组件根据配置的 MaxStack 分批调用现有快速添加接口。每一批仍是独立事务、独立版本和通知；已经成功入包的批次保留。快速添加保持原规则：寻找第一个适配的空位置，网格初始方向失败后按配置尝试旋转，**不自动合并已有栈**。同类物品拖放堆叠仍使用已有堆叠接口。

世界掉落只有在收到成功结果后才扣减对应数量；全部接收后销毁。满包、未知配置等失败不会扣减世界物品。混合清单逐条处理，放不下的武器不会阻止后续可入包材料；失败条目保留。处理中的重入及已拾取对象的重复调用不会重复入包。

拾取交互设置 `dismiss_prompt_after_interact = false`，使部分成功和满包后的提示继续可见。腾出空间后，对同一掉落再次按 E 即可重试。其他既有交互使用默认的一次交互后隐藏提示规则。

其他奖励系统可以在角色 ready 后调用同一入口，并根据结果处理剩余数量：

```gdscript
var backpack := PlayerInventoryComponent.find_for(hero)
var result := backpack.receive_item(21, 250)
if result.is_ok():
    var received: int = result.payload
    print("实际入包数量：", received)
else:
    print(result.message)
```

如需世界掉落，通过已有组件生成；不直接创建背包实例：

```gdscript
drop_component.create_dropped_item(
    [{"id": 21, "amount": 250}], spawn_position)
```

## 生命周期与输入

| 时机 | 背包行为 |
| --- | --- |
| 从主菜单开始游戏 | `PlayerInventorySession.start_new()` 显式重建空容器 |
| 直接运行 Home、关卡或接入测试台 | 角色组件通过 `ensure()` 首次创建；已有则复用 |
| 切换场景、重建或销毁角色 | 保留容器、物品实例 ID、数量和版本 |
| Tab / Esc / 关闭按钮关闭背包 | 解除窗口数据订阅，取消未提交拖拽，保留业务数据 |
| 退出游戏进程 | 会话结束；本次接入不包含磁盘存档与读档 |

背包打开时阻止移动、攻击及 E 拾取，世界继续运行。Tab 属于 UI 输入，因此背包打开后仍能再次关闭；关闭按钮获得焦点时也可用。暂停、结果、加载界面和 UI 快捷键屏蔽请求优先，防止操作下层背包。现有 UIManager 负责窗口所属场景、遮罩和输入恢复。

## 自动测试内容与方法

`tests/inventory/gameplay_spec.gd` 使用场景声明的角色夹具、正式资源、正式 Manager、掉落工厂、物理区域、InputController 和 UIManager。通过真实键盘、鼠标事件验证行为，并读取快照、版本和地面清单核对结果。

| 测试内容 | 验证方法 |
| --- | --- |
| 配置与初始化 | 检查正式武器/材料占位、旋转、栈上限；重复 ensure 前后比较完整快照 |
| 物理检测与提示 | 生成真实掉落，等待物理帧，检查检测目标、图标、数量和提示文本 |
| 超上限及部分接收 | 2 × 1 容器拾取 250，断言入包 200、地面 50、两栈合法，生成器原始数组保持 250 |
| 满包重试与恢复 | 再按 E，完整快照及版本不变；删除一栈后再拾取，地面对象销毁、检测目标清理 |
| 混合清单与失败 | 放不下的武器保留，合法材料继续入包；未知 ID、零数量返回对应错误 |
| 重入与重复调用 | 在 Manager 变更通知回调中再次 collect，以及排队销毁前重复 collect，断言无重复物品 |
| 正式 UI 与输入 | Tab 打开正确容器，E 被屏蔽；按钮聚焦时 Tab 关闭；关闭后 E 恢复 |
| 暂停与快捷键屏蔽 | 上层暂停优先、Esc 关闭暂停后背包仍在；快捷键屏蔽令牌阻止打开背包 |
| 关闭中的拖拽 | 实际鼠标发起拖拽后按 Tab，断言拖拽取消、完整快照不变、数据订阅解除 |
| 切关与新游戏 | 两次实际 `change_scene_to_packed()`，检查旧角色销毁、窗口关闭、实例及版本保留；start_new 后清空且版本归零 |
| 正式 Hero 场景 | 实例化真实 Hero.tscn，验证组件和 8 × 6 配置、接收入口、掉落工厂，销毁角色后容器仍存在 |

## 手动验证

在编辑器打开 `Scene/Inventory/InventoryGameplayLab.tscn`，按 F6：

1. 等待角色启动，场景会在身旁生成材料 ×250；按 E，Tab 打开背包，应看到 100、100、50 三栈。
2. Tab 关闭，点击“生成长剑 ×1”，按 E 拾取；再次打开背包，应显示 1 × 3 的武器占位。
3. 拖动物品时按 R 旋转；同类拖放默认堆叠，不同物品拖放交换；中键取一半，左键放置，右键或 Esc 取消。长按背包边框可移动窗口，滚轮可查看超出窗口的网格。
4. 反复生成并拾取物品直到背包放不下，确认未入包数量保留在地上。调整背包腾出空间后，关闭背包再按 E，可继续拾取。
5. 背包打开时按 E 应无拾取；Tab 关闭后可拾取。Esc 在物品拖拽中先取消拖拽，再按可关闭背包。
6. “重置测试背包”会显式开始空会话并移除测试台世界掉落，方便再次测试。

原 `InventoryLab.tscn` 继续用于添加自定义容器和快速添加物品的表单测试；新的 GameplayLab 侧重玩家、世界拾取和正式 UI 的完整链路。
